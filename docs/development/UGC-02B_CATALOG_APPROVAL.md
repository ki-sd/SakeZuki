# UGC-02B 이미지 없는 카탈로그 승인

## 식별 및 충돌 정책

내부 PK는 MySQL이 생성한 `no`이고, 외부 키는 V6 출처 원장이 관리한다. USER_SUBMISSION에는 실제 외부 키가 없어 원장 외부 키와 기존 `source_id`를 NULL로 둔다. v1 승인 식별은 양조장의 검수된 일본어 이름, 브랜드의 양조장 내부 번호와 검수된 일본어 이름, 사케의 양조장 내부 번호와 검수된 일본어 이름을 각각 고유 예약한다.

식별용 이름에는 Unicode NFKC, 양끝 Unicode 공백 제거, 연속 공백 하나로 축약, Locale.ROOT 소문자화를 적용한다. 가나와 탁음은 별도로 치환하지 않는다. 표시명과 리비전 원문을 보존한다. DB의 기존 ai_ci 동등 비교는 보수적인 추가 충돌 신호다. 기존 목록의 부분 일치와 중복 후보의 접두·순위는 최종 승인 판정에 사용하지 않는다. 관계는 일본어 또는 한국어 이름의 충돌을 확인한다. 상품은 선택한 양조장의 전체 상품과 일본어 이름을 대조한다.

v1의 예약 단위는 **확정 양조장과 정규화된 일본어 표시명**이다. 브랜드, 용량, 변형, 주미, 특정명칭은 확인된 구분 근거로 보존하지만 단독으로 같은 이름의 충돌을 해제하지 않는다. 시드에는 구조화된 용량·변형과 검증된 SKU가 부족해 이 단계는 동명이품을 자동 병합하거나 별도 상품으로 자동 승인하지 않는다. 새 버전의 상세 식별 정책을 도입하기 전까지 충돌은 기존 연결 선택, 보완 또는 수동 판정으로 돌린다. NULL은 동일성의 증거로 쓰지 않는다. 승인에는 해당 불변 리비전의 식별을 확인했다는 명시적 표시가 필요하다.

V13의 nullable 키는 승인 생성 행에만 기록한다. 키는 UTF-8 `catalog-name-v1\n` 뒤 단일 정규화 이름을 연결한 SHA-256의 32바이트이며, 소속 번호는 복합 UNIQUE의 별도 열이다. 비교는 바이너리다. 기존 원문에서 정규화 값을 재현할 수 있고, 해시가 같으면 원문에 대한 동일성 추정·병합 없이 충돌로 처리한다. 기존 행을 자동 등록하지 않는다. V9 잠금을 획득한 뒤 기존 행도 범위 내에서 직접 읽어 v1 비교 및 MySQL 동등 비교를 적용한다. 기존 행에는 backfill이나 이름 변경이 없다.

격리 MySQL 8.4.13의 전체 시드 10,337건에 실제 Java v1 정규화를 읽기 전용으로 적용했다. 원문 기준 동일 양조장·이름은 3그룹 6건, v1은 4그룹 8건이었다. 그중 1그룹은 서로 다른 원문이 정규화 후 합쳐졌다. MySQL 기존 ai_ci의 양조장·이름 기준에서도 4그룹 8건이었다. 이름을 양조장 구분 없이 묶어도 ai_ci 충돌은 4그룹 8건이었다. v1 단일 후보는 10,329건이며 기존 상품의 독립적인 동일성 검수가 완료됐다는 뜻은 아니다. 양조장은 905건, 브랜드는 1,525건, 브랜드 없는 상품은 0건이었다. 10,337건 전부 신규 구조화 용량·변형이 미입력 상태였다. 이 조사에서 기존 상품을 수정하거나 병합한 건수는 0건이다.

## API, 출처 및 공개 데이터

`POST /api/admin/sake-submissions/{id}/approvals`는 UUID `Idempotency-Key`와 엄격한 JSON의 `expectedVersion`, `revisionNo`, `reason`, `identityConfirmed: true`를 받는다. 요청에 공개 상품 데이터는 받지 않는다. 표시값이나 관계가 바뀌면 먼저 관리자 리비전을 생성한다. 첨부가 남아 있으면 409와 함께 첨부를 명시적으로 제외한 관리자 리비전을 안내한다. 기존 리비전과 이미지 이력은 보존한다.

실시간 관리자 권한 검증을 통과한 같은 행위자의 동일 요청은 HTTP 200으로 `id`, `status`, `version`, `currentRevision`, `sakeNo`, `approvedAt`을 재생한다. 다른 제보·버전·리비전·사유·확인 조건을 같은 승인 키에 사용하면 409다. 신규 승인에는 PENDING과 현재 리비전·기대 버전 일치가 필요하다. V12의 결정 테이블과 별도 `SUBMISSION_APPROVAL`을 두어 기존 반려·보완 계약을 보존한다. 키 범위는 행위자와 API 종류다. 같은 UUID를 기존 결정 API의 키로도 쓸 수 있다. 승인 원장은 제보 PK, 불변 리비전 복합 FK, 공개 사케 FK, 관리자 FK, 버전·요청 해시·사유·시각을 저장한다. 하나의 공개 상품을 서로 다른 승인 영수증에 다시 연결할 수 없다.

확정 기존 관계의 소속을 쓰기 잠금 아래 다시 확인하며 기존 양조장·브랜드의 필드나 출처를 갱신하지 않는다. 신규 양조장·브랜드 및 사케는 `USER_SUBMISSION` 출처를 갖는다. 원장의 `submission:{id}/revision:{n}` 증거가 승인 원장과 감사 기록으로 연결된다. 사용자 URL은 사케의 미검증 출처로만 보존하고 서버가 가져오지 않는다. 상품 URL을 양조장·브랜드 URL에 복제하지 않는다. 이미지 URL이나 공개 자산을 생성하지 않으므로 상세의 기존 이미지 대체 표시와 호환된다.

V1의 이름 500/1,000자 및 수치 문자열 100자 계약과 V8 nullable 외부 키를 유지한다. 수치 미입력은 NULL이다. 단일값은 정밀도를 유지한 10진수 문자열, 범위는 `min ~ max`로 저장한다. 용량과 변형은 V13의 nullable `capacity_ml`, `variant`에 저장하고 상세 응답에 선택적으로 추가한다. 추천 프로필은 단일값을 닫힌 구간으로, 범위는 입력 양 끝 그대로 기록한다. 기존 정수부 용량을 유지하면서 프로필의 DECIMAL 소수부를 3자리로 늘렸다. Tools 파서는 이 문자열의 양수·음수와 범위를 해석할 수 있다. 역사적 일괄 생성기는 기존 행에 재삽입하는 도구이므로 승인 프로필의 동기화 작업으로 실행하지 않는다.

추천 후보와 저장 추천의 양조장 조회는 SAKE의 FK를 직접 사용한다. 조건 없는 점수는 0이고, 존재하는 조건만 점수식에 추가한다. 기존 점수 3/2/2/1과 최대 40건, NULL 수치 제외 및 동점 내부 번호 순서를 유지한다. 신규 프로필은 승인과 동시에 이후 후보 조회에 들어간다. 기존 추천 캐시나 크레딧 원장은 갱신하지 않는다.

## 트랜잭션과 운영 경계

READ COMMITTED에서 `MEMBER(행위 관리자) → MEMBER_AUTHORITY → CATALOG_SUBMISSION → V9 mutex → 카탈로그·관계 및 출처·프로필 → 승인 원장·상태·감사 이벤트` 순서다. 잠금 이후 읽은 전체 관련 카탈로그에서 충돌을 확인한다. 같은 제보나 같은 최종 식별자로 경합하면 원장과 UNIQUE가 다시 방어한다. 승인 원장·감사 이벤트의 FK는 이미 잠근 관리자, 제보 및 불변 리비전과 새 사케를 참조한다. 소유 회원 행을 추가 잠금하지 않는다. 현재 V9 Tools 수집 경로는 mutex 뒤 회원·제보를 잠그지 않는다.

1213은 InnoDB가 트랜잭션을 롤백하며, 1205는 기본 설정에서 실패 문장만 롤백하므로 Spring 트랜잭션 경계로 예외를 전파해 전체를 롤백한다. Backend는 부분·자동 재시도를 하지 않는다. 커밋 결과가 불확실하면 동일 승인 키로 영수증을 먼저 재확인하는 경로를 쓴다. Tools의 기존 전체 트랜잭션 재시도 계약을 변경하지 않았다.

동시 카탈로그 등록에는 V9를 준수하는 현재 쓰기 경로만 사용한다. 승인 트랜잭션은 앞서 커밋한 Guide 작업을 검사한다. 이후 새로운 외부 ID로 들어오는 Guide 수집은 자체 출처 계약을 사용하므로 UGC 승인명을 대상으로 반대 방향 대조를 자동 적용하지 않는다. 운영에서 신규 Guide 일괄 등록과 UGC 승인을 병행하기 전에 신규 Guide 배치와 UGC 승인 상품의 충돌을 검토한다. 구버전 Tools와 직접 원장 쓰기 차단은 기존 선행 조건이다.

V13은 InnoDB DDL 여러 개를 포함한다. 적용 중 실패하면 Flyway 이력과 각 테이블의 실제 DDL을 대조하고 전용 복구 창에서 백업 복원 또는 기술 검토한 복구를 수행한다. 이미 완료된 ALTER를 전제로 무조건 repair 후 다시 실행하지 않는다. 운영 적용 및 외부 호출은 이 검증 범위에 포함하지 않았다. UGC-02C는 검증된 DELIVERY 객체를 연결할 때 같은 공개 등록 트랜잭션과 승인 원장을 재사용할 수 있도록 권리·세대·객체를 재검증해야 한다.

## 검증 명령과 증거

기준 main은 `aca186edd146dae725ad68f34a757a00a5b714b9`다. V1–V12는 기준 main과 바이트 단위로 동일하다. `python3 scripts/test_auth_integration.py --e2e`의 격리 MySQL 단계에서 Backend 기본 28건, Backend MySQL 87건, Tools MySQL 17건을 통과했다. 기존 78건의 Backend MySQL 검증에 V13 설치·업그레이드 1건 및 승인 HTTP 8건이 추가됐다. 승인 검증에는 역할 철회 후 재생 차단, 현재 리비전·버전 및 데이터 고정, 이미지 이력, 신규·기존 이름 충돌, V9 대기, 관리자 두 명의 관계·상품 경쟁, 같은 키 재생, 감사 저장 실패의 전체 롤백 및 같은 키 복구가 포함됐다. 추천 SQL은 실제 MyBatis/MySQL에서 빈 조건과 일부 조건, 브랜드 없는 승인 상품 및 저장 추천을 검증했다. 다음 독립 QA에서는 기존 카탈로그의 중복 판정, V9 쓰기 경쟁, 권한 철회와 승인 간 순서, 장애 후 영수증 재생을 집중 확인한다.
