## P1 카탈로그 조회 계획

관리 URL 뷰의 SELECT 내부 상관 서브쿼리가 derived merge를 막았다. 상세·추천 등이 SAKE를 이미 조회한 상태에서도 뷰가 전체 카탈로그를 한 번 더 읽었다. 뷰를 제거하고 같은 SAKE 행에서 공통 MyBatis SQL 조각으로 대표 이력을 조회한다. 관리 이력이 전혀 없는 카탈로그에서는 한 번의 비상관 확인 후 기존 URL을 사용한다. 이미지 유무·검색 일치도·번호 정렬은 LIMIT과 OFFSET 전에 그대로 적용한다. 유료 스냅샷은 중복 번호를 제거한 한 쿼리로 관리 이력을 읽으며 관리 이력이 없는 기존 스냅샷 이미지 값은 보존한다.

격리 MySQL 8.4.13의 동일 인스턴스에 시드 10,337건을 복제했다. 실제 MyBatis MappedStatement.getBoundSql에서 상세 번호 1, 목록 OFFSET 0·108, 검색어 준마이, 추천 3건과 투영 SQL을 추출했다. 이전 스냅샷은 JDBC의 실제 단건 쿼리, 수정 코드는 3건 입력의 배치다. 각 조합에서 워밍업 2회 뒤 7회의 EXPLAIN ANALYZE를 비교했다. 기존 PR과 수정 SQL의 상세·목록·검색·추천 출력은 각 분포에서 순서까지 일치했다.

## P1 객체 무결성

| 상황 | 객체 처리 |
| --- | --- |
| 응답 중단·시간 초과·권한 또는 연결 장애 | 기존 VERIFIED와 세대 유지. 진행 중 작업만 RETRYABLE_FAILURE |
| 확정적인 404 | 해당 객체만 RETRYABLE_FAILURE로 전이. 권한 있는 작업이 동일 키의 조건부 생성과 검증으로 복구 |
| 바이트·MIME·해시·메타데이터 불일치 또는 한도 초과 | 해당 객체의 검증 정보를 비우고 PERMANENT_FAILURE. 공개 뷰·새 연결·목록·재열람에서 제외 |
| STAGING 장애 | STAGING에만 기록. 원본이 확인되기 전에는 새 DELIVERY 시도를 만들지 않는다. 기존 정상 DELIVERY 및 그 연결 유지 |
| 운영자 복구 | 같은 자산·영역·키·버전을 읽기 전용 revalidate로 확인. DELIVERY는 유효 권리가 필요하고 공개 뷰는 기존 활성 연결과 최신 권리를 확인 |

네트워크 I/O는 커밋 후 수행한다. 성공·실패는 객체 ID, 상태, attempt 세대 조건으로 기록한다. 정상 VERIFIED 객체의 재검증 중에도 공개 상태를 유지한다. 공개 GET은 실제 읽은 응답에 대한 확정적 문제만 조건부 갱신하며 PUT을 수행하지 않는다. 세대가 바뀐 뒤 도착한 실패와 동시에 반복된 실패는 최신 상태를 변경할 수 없다. 전송 전 동일한 활성 연결과 객체를 다시 확인한다.

## P2 공개 경로와 브라우저

사케 번호와 UUID는 게이트웨이에서 검증한다. 잘못된 문자열·축약 UUID·범위 초과·음수는 DB 또는 스토리지 조회 전에 400이며 존재하지 않는 대상은 404다. 오류에도 no-store·nosniff를 유지한다. 실제 서버 예외는 기존 오류 경로를 사용한다.

공통 이미지 컴포넌트는 URL이 바뀌면 이전 렌더러 및 오류 상태를 폐기한다. 상세도 공통 fallback을 사용한다. 같은 화면에서 정상·404·503·URL 교체·늦은 오류·철회 후 null을 모의 응답으로 검사한다. 플레이스홀더 자체의 실패는 반복 요청을 만들지 않는다. 기존 크기 클래스와 unoptimized를 유지하고 격리 Chromium은 원격 이미지 호스트를 찾아가지 않는다.

## 남은 기술 부채와 재검증

스냅샷 N+1은 묶음 쿼리로 해소했다. SAKE_IMAGE의 DELIVERY 영역 DDL 강제, 철회·복제 경쟁에서 참조되지 않은 객체 정리, 권리 연장 후 명시 재공개, 저장 중 중복 디코딩은 후속 작업이다. 운영 활성화에는 기존 추천 SQL 수정, 구버전 Tools 쓰기 차단, V9 잠금 계약 준수가 여전히 필요하다.

Antigravity 재검증의 중점 범위는 120건·혼합 분포의 상세 및 후속 페이지 계획, 저장 영역별 바이트와 메타데이터 손상, 공개 GET과 명시적 복구 경합, 교체·철회 후 재열람, 동일 브라우저 화면의 URL 변경이다.
