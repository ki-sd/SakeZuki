# UGC-02C 이미지 포함 승인과 영속 승격

기준 main `59b6fc239b7531f7050c620312f3370ae59b33f1`에서 V14를 추가한다. [PR #18의 최종 독립 QA 및 병합](UGC-02B_CATALOG_APPROVAL.md#최종-독립-qa-및-병합)

## API와 권리 근거

| 관리자 요청 | 계약 |
| --- | --- |
| `POST /api/admin/sake-submissions/{id}/approvals` | 기존 이미지 없는 승인 200 및 영수증 재생 |
| `POST /api/admin/sake-submissions/{id}/image-approvals` | 엄격 JSON, UUID 멱등 키, 승인 작업 202 및 상태 조회 Location |
| `GET /api/admin/sake-submissions/{id}/approval-job` | 최신 작업과 완료 영수증 |
| `GET /api/admin/sake-submissions/{id}/approval-job/{job}` | 특정 이전 작업 추적 |
| `POST /api/admin/sake-submissions/{id}/approval-job/{job}/retry` | 원래 관리자가 재시도 가능한 작업의 다음 시각을 앞당김 |
| `POST /api/admin/sake-submissions/{id}/approval-job/{job}/cancel` | 현재 관리자가 활성 작업 중단, 중단 관리자 보존 |

요청 몸체는 `expectedVersion`, `revisionNo`, `reason`, `identityConfirmed: true`, `attachmentId`, `rights`를 받는다. `rights`의 필드는 `decision: "GRANTED"`, `scope: "PUBLIC_WEB"`, `evidence`, ISO-8601 UTC `validFrom`, 선택 `validUntil`이다. MySQL UTC 시각을 기준으로 이미 발효되고 만료되지 않은 근거를 받으며 소수 초 최대 6자리까지 지원한다. 상품 원문 및 사용자 동의는 불변 리비전에서 읽는다. 입력 형식이나 잘못된 권리 기간은 422, 현재 상태·버전·첨부·권리·멱등 조건의 충돌은 409다. 마스터 설정은 기본 비활성이고 신규 요청에 503을 반환한다. 이미 기록된 작업은 현재 관리자 권한으로 조회·중단할 수 있다.

사용자 동의·설명과 관리자 판단은 별개다. 등록 시 제보 행 아래 현재 리비전의 READY 첨부와 검증된 STAGING을 확인하고, 자산 잠금 아래 권리 이벤트와 작업을 함께 커밋한다. 철회·거부로 가려진 STAGING은 승인 대상으로 사용할 수 없다. GRANTED는 검토한 증거의 기록이다. 공개 제공에는 검증된 객체와 최종 활성 참조가 함께 필요하다. 중단·검수 필요 상태에서 이벤트는 기록으로 남는다. 작업은 정확히 자기 이벤트만 사용하고 새 요청은 명시적인 새 검수와 새 이벤트를 요구한다. 사용자 동의와 첨부 이력은 수정하지 않는다.

이미지 승인과 이미지 없는 승인은 관리자별 UUID 공간을 공유하고, 기존 반려·보완 키 공간은 독립적이다. 같은 이미지 요청 키·해시는 동일 작업의 현재 상태를 반환한다. 다른 본문·리비전·제보·모드로 키를 바꾸어 쓰면 409다. 최종 영수증은 V13 승인 원장을 그대로 사용한다.

## V14 및 작업 전이

V14는 리비전과 첨부의 귀속, 자산·STAGING·DELIVERY 객체와 권리의 귀속, 최종 영수증과 제보의 귀속에 복합 FK를 둔다. 활성 상태의 생성 열에는 제보 UUID가 들어가므로 UNIQUE가 제보당 하나의 활성 작업을 강제한다. 완료·중단·검수 필요 상태의 NULL은 MySQL UNIQUE에서 서로 중복될 수 있어 이력을 보존한다. CHECK는 작업 시각과 완료 결과, 중단 행위자, 실패 코드 및 시도 횟수의 일관성을 검증한다. 외부 객체의 상태와 권리의 시간 유효성은 실행 시 확인한다. V14에 여러 DDL 문장이 있어 각각의 적용 상태를 확인해 복구한다.

- **PENDING → PROCESSING**은 5초 주기 한 건 polling과 READ COMMITTED의 `FOR UPDATE SKIP LOCKED`로 획득한다. 종료 상태의 기한은 CHECK에 따라 NULL이다. `(due_at, id)` 인덱스의 기한 범위를 같은 순서로 읽어 상태들을 정렬하는 별도 스캔 없이 실행 가능한 후보 하나를 고르고 잠금 중인 작업은 건너뛴다. DB UTC로 generation과 시도 횟수를 올리고 240초 임대를 설정한다.
- **PROCESSING → RETRYABLE_FAILURE**는 저장소 미설정/일시 I/O, 또는 확정된 MySQL 1205·1213에 사용한다. 최초 세 번의 지연은 30·60·120초이며 4회 소진 후 검수 필요 상태로 종료한다. 만료된 PROCESSING도 시도 한도 내에서 다시 획득할 수 있다.
- **REQUIRES_REVIEW**는 영구 무결성 실패, 권리·관리자·리비전 변화, 카탈로그 충돌, 확인이 필요한 DB 실패 또는 시도 소진을 표시한다. 활성 작업이 해제되어 제보 변경 및 새 검수가 가능하다.
- **CANCELLED**는 현재 관리자 중단으로 generation을 무효화한다. 재시도 상태를 포함한 활성 작업 중에는 사용자 취소·보완과 관리자 수정·반려·보완 요청·이미지 없는 승인·다른 작업 등록을 같은 제보 행 잠금 아래 차단한다.
- **COMPLETED**는 V13 영수증과 공개 등록의 트랜잭션에서만 전이한다.

작업 획득·시도는 트랜잭션 외부 스토리지 단계와 분리된다. 설정 `UGC_IMAGE_APPROVAL_ENABLED=true`는 명시적인 운영 활성화가 필요하며 `UGC_IMAGE_APPROVAL_POLL_MS` 기본값은 5000이다. 전용 단일 스케줄러가 신용·인증 작업을 위한 스케줄러와 분리된다. 종료 시 새 작업 획득을 중단하고 미완료 임대는 재기동 후 회수된다. 기존 R2 연결·소켓·SDK 호출 타임아웃을 재사용한다. SDK 호출 상한 40초의 GET/조건부 PUT/GET 검증을 감안해 240초 임대를 사용한다. 작업이 많은 경우 한 poll당 한 번의 처리와 유한한 재시도로 소비량을 제어한다.

## 객체 세대, 공유 자원, 공개 잠금

승격은 기존 변환 바이트를 STAGING GET으로 읽어 MIME·길이·메타데이터·실제 SHA-256·이미지 payload를 검증한다. 동일한 결정적 키를 사용하여 DELIVERY 조건부 PUT 및 GET 검증을 한다. 다른 바이트나 메타데이터로 기존 객체를 덮어쓰지 않는다. DELIVERY intent ID는 PUT 전 작업에 기록한다. 응답 유실로 객체가 이미 존재하면 검증 후 재사용한다.

STAGING 읽기 준비, DELIVERY intent 및 V10 attempt 변경, VERIFIED 또는 실패 DB 기록마다 작업 행부터 잠그고 정확한 generation을 검사한다. 다음으로 자산을 잠그고 원래 권리 이벤트와 STAGING의 정확한 VERIFIED attempt를 확인한다. 작업 행의 잠금과 V10 갱신은 같은 짧은 트랜잭션이다. 외부 요청 중에는 행 잠금이 없으며 지연된 작업자의 네트워크 요청 자체는 취소되지 않을 수 있다. 이전 작업의 상태·세대 기록과 최종 공개는 무효화된다. UGC-01의 여러 JVM 사이 업로드 임대와 V10 attempt 교차 문제는 별도 과제다.

이미지 서비스의 JVM당 1개 permit을 사용자 업로드와 Worker가 공유한다. 업로드는 permit 이후 회원 쿼터를 예약한다. Worker는 permit을 확보하지 못하면 임대 및 시도를 소비하지 않고 다음 poll로 넘어간다. 기존 HTTP 업로드 1슬롯과 비공개 미리보기 2슬롯, 공개 이미지 4슬롯은 유지한다.

최종 공개는 `MEMBER → MEMBER_AUTHORITY → CATALOG_SUBMISSION → 작업 → V9 → IMAGE_ASSET → STAGING → DELIVERY → 카탈로그/SAKE_IMAGE → 승인 원장 → 제보 상태·감사 → 작업 완료` 순서다. 작성자 관리자와 권한, 현재 불변 리비전·첨부, 임대와 세대, 권리 및 두 객체를 다시 확인한다. 미커밋 카탈로그는 외부에 보이지 않는다. V9 재진입은 이미 잡은 행을 확인하며 기존 CatalogRegistration을 재사용한다. 새 SAKE의 PK는 이미지 연결 이전에 생성되고 다른 트랜잭션에 공개되지 않는다. 기존 공개 연결·권리 기록 경로는 자산을 먼저 잠그며 작업·V9를 역방향으로 획득하지 않는다. Tools는 V9 후 기존 카탈로그만 만진다. FK 검사는 기존에 잠근 작업 관련 행 또는 불변 참조를 대상으로 한다.

최종 트랜잭션 밖에서만 스토리지를 읽고 쓴다. 1205의 문장 롤백 및 1213은 Spring 전체 롤백 경계 이후 승인 HTTP에서 503 또는 Worker 재시도로 전달된다. 다른 SQL 예외는 이 범주에 넣지 않는다. 완료 커밋 응답 유실은 같은 키로 작업·영수증을 확인한다. 정체된 작업은 임대와 시도 한도로 복구되며 실패 기록은 현재 PROCESSING과 generation에만 적용된다.

## 미참조 객체, 권리 철회 및 운영 경계

관리자 조회는 작업·자산·DELIVERY 객체 ID·시도 시각·권리 유효성·활성 참조를 보여 준다. 실패 후 남은 저장소 객체는 비공개이고 새 요청이 같은 바이트를 검증하면 재사용할 수 있다. 물리 삭제는 후속 승인 대상이다. 실제 삭제 설계는 활성 공개 참조, 실행 중 또는 재시도 가능한 작업과 다른 검수에서 공유하는 객체를 보호해야 한다. 이 PR에는 물리 삭제 경로가 없다.

기존 공개 게이트웨이의 GET 검증과 권리·참조 재확인, no-store 및 nosniff, 추천 이미지 projection을 유지한다. 권리 만료·철회 뒤 이미지를 대신할 레거시 URL을 만들지 않는다. 이미 전송한 사본은 회수할 수 없다.

운영 활성화 전에 서로 다른 비공개 STAGING·DELIVERY 버킷과 최소 권한, V13·V14 적용 계획과 DB 백업, 신규 Guide 배치의 UGC 충돌 검수, 구버전 Tools·레거시 일괄 추천 프로필 생성기·직접 SQL 통제를 확인한다. Guide가 선행하면 UGC가 충돌을 확인한다. 이후 새로운 Guide 외부 ID를 쓰는 경로의 반대 방향 대조는 후속 작업이다. PR #18의 정규화·정밀도 및 후보 정책 범위도 유지한다. UGC-03은 사용자 동의와 관리자 권리 판단을 분리하고 202의 Location을 조회한다. 활성 작업 중 변경 409, 재시도·중단 및 완료 영수증을 화면에 반영한다.

## 검증과 독립 QA 인계

격리 MySQL 8.4.13과 분리 Fake Storage를 사용한다. 테스트의 저장소 구현은 GET·PUT마다 활성 트랜잭션이 없는지 확인한다. 기존 합성·모의 S3 테스트를 유지한다. HTTP 경로에서 등록·중복·권리·리비전·작업 중 변경 차단과 완료 영수증을 검사한다. 실제 MySQL에서 V13→V14와 빈 DB 적용, UNIQUE·FK·CHECK, 두 연결의 동시 획득, 만료된 이전 generation, V10 attempt 보호, V9 1205 및 동일 작업 회복을 재현한다. 등록 실패의 권리 롤백, 최종 참조·원장·감사·작업 완료의 실패 후 전체 롤백, 손상·응답 유실·재시도 상한, 사용자 permit 경합을 검증한다. 하네스와 최신 CI 링크는 PR 증거를 참조한다.

독립 QA는 별도 JVM 간 임대 경합, 권리 철회와 최종 커밋 양방향 경쟁, 스토리지 장기 정지 뒤 이전 응답, 미커밋 공개 읽기, 1213, 순차·동시 Guide 쓰기와 배치 부하에 집중한다. 실제 R2, 운영 DB, OCI 및 Gemini는 검증에 사용하지 않았다.
