## 데이터 모델과 출처

- **IMG-03B 기반**에 `IMAGE_ASSET`(내부 ID, 출처·증거, 처리·권리 상태, 원본·변환 SHA-256/MIME/길이/해상도, 변환 버전), `IMAGE_OBJECT`(자산 FK, 저장 영역·버전·객체 키, 검증 시각, 상태, 영역·키 UNIQUE), `SAKE_IMAGE`(공개 상품 FK, 선택 자산·객체 FK, 활성·철회 상태), 별도 변경 불가 권리·감사 이력을 제안한다. 한 상품의 활성 대표 이미지는 한 개로 제한한다. 작업 임대·시도·오류는 durable job/outbox에 기록한다. 기존 `SAKE.image_url`은 외부 링크 호환 필드로 유지하되 관리 자산 철회 후 무단 fallback은 차단한다.
- **카탈로그 출처**는 `SAKE_SOURCE`, `BREWERY_SOURCE`, `BRAND_SOURCE`처럼 대상별 실제 FK가 있는 연결로 분리한다. 외부 식별값은 `(source_system, external_key)`로 범위를 나누고 명시적인 대소문자·정규화 규칙을 적용한다. 각 테이블에 canonical URL, 관찰·검수 증거와 시각을 저장한다. 기존 source_id는 SAKE_GUIDE로 backfill한다. USER_SUBMISSION·ADMIN은 승인 이벤트와 연결하고 외부 값 없이 출처를 기록한다. BREWERY_OFFICIAL은 확인된 값 또는 URL을 사용할 수 있다. 가짜 외부 ID를 발행하지 않는다.
- **전환 순서**는 새 마이그레이션으로 출처 연결 추가·backfill → 데이터 건수, 누락·중복, 기존 FK 검증 → 수집 도구를 SAKE_GUIDE 연결에 한정하고 기존 자동 갱신 필드 소유권 확인 → 기존 `source_id`를 nullable UNIQUE 호환 컬럼으로 완화하여 승인 insert에서 NULL을 허용하는 순서다. 이 기간에는 기존 reader의 NULL 처리와 호환 쓰기를 검증하고, 옛 도구가 사용자 행을 읽거나 수정할 수 있다면 기능을 활성화하지 않는다. 이름 기반 수집 upsert를 금지하고 매핑된 기존 원본만 갱신한다. V1–V5 및 적용된 마이그레이션은 그대로 둔다. 안정화 이후 호환 컬럼 제거는 별도 검토다.
- **UGC-01**은 `CATALOG_SUBMISSION`(소유 회원 FK, 요청 종류·대상 번호, 현재 리비전, 상태, 버전, 시각), 불변 `SUBMISSION_REVISION`(번호, 부모 리비전, 작성자·역할, 스키마 버전, 검증된 payload, 원본/사용자 보완/관리자 수정 구분), `SUBMISSION_EVENT`(전후 상태, 관리자·사용자, 사유, 시각), `SUBMISSION_ATTACHMENT`(비공개 자산·소유권)으로 제안한다. 최초 제출 리비전을 보존한다. 승인 매핑 테이블에는 요청당 UNIQUE와 승인한 리비전 및 실제 공개 상품 번호를 기록한다. 처음에는 CREATE_SAKE만 수락하고 향후 EDIT_SAKE·REPLACE_IMAGE는 대상 내부 번호와 대상 버전을 둔다.
- **입력 제안**은 사케 일본어·한국어 이름을 필수로 하고, 양조장은 기존 번호를 선택하거나 신규 일본어·한국어 이름을 입력한다. 기존 브랜드 선택·신규 브랜드 정보·브랜드 없음은 별도 경우다. 브랜드가 선택 양조장에 속하는지 서버에서 검증한다. 선택 필드는 사케·양조장 가나, 브랜드 일본어·한국어 이름, 특정명칭, 니혼슈도·산도·정미율·알코올 도수, 주미·효모 일본어·한국어 이름, 용량·상품 변형, 이미지, 정보 출처 URL·이미지 권리 근거·설명이다. 미확인 수치는 NULL로 보존한다. 확인한 수치는 단위와 범위를 검증하며 공개 DTO의 기존 단위 표현은 유지한다. 권리 근거가 부족하면 이미지 보류와 이미지 없는 승인, 또는 보완 요청을 검토할 수 있다.

## 승인 상태와 트랜잭션

| 상태 전이 | 제안 규칙 |
| --- | --- |
| 신규 → `PENDING` | 인증된 회원이 제출한다. 첨부 참조는 같은 회원이 발급받은 유효한 비공개 자산만 허용한다. |
| `PENDING` → `NEEDS_REVISION`·`REJECTED` | 관리자가 사유와 검토 리비전을 기록한다. 관리자 수정 시 원본 위에 새 리비전을 추가한다. |
| `NEEDS_REVISION` → `PENDING` | 소유자가 수정본을 새 리비전으로 제출한다. 기존 검수는 수정본에 승계하지 않는다. |
| `PENDING`·`NEEDS_REVISION` → `CANCELLED` | 소유자가 취소한다. 공개 완료 및 종료 상태는 그대로 잠그고 정정은 새 제보에서 처리한다. |
| `PENDING` → `APPROVED` | 관리자가 특정 리비전을 선택한다. 이미지 작업이 있으면 별도 publication job이 `PREPARING` 상태로 진행하며, 공개 DB 트랜잭션이 커밋된 뒤 승인으로 표시한다. |

모든 쓰기는 기대 버전으로 비교해 오래된 화면의 결정을 `409`로 처리한다. 승인 시작 시 MySQL 트랜잭션에서 제보를 잠그고 권한·상태·리비전을 다시 확인한 뒤 `(submission_id, revision)` UNIQUE 승인 작업을 등록한다. 동일 Idempotency-Key와 동일 payload는 같은 결과를 반환하고, 같은 키와 다른 payload는 거부한다. 진행 중 보완·취소는 초기 제안상 충돌 응답으로 처리하고, 실패 후에는 새 결정 또는 같은 작업 재시도를 지원한다.

최종 트랜잭션은 먼저 제보·작업을 잠그고 승인할 버전과 승인 관리자 자격, 매핑·권리 유효성, 객체 검증 결과를 확인한다. 기존 상품 중복 검색은 일본어 이름·양조장·브랜드 외에도 용량·라벨·상품 변형·확인된 외부 ID를 보여 준다. 다른 제보에서 동시에 같은 상품을 만들지 않도록 카탈로그의 검수된 정규화 식별 조합(양조장, 제품명, 확인된 변형 식별자)을 별도 UNIQUE 등록표로 잠근다. 기존 데이터의 정규화 충돌은 초기 적재 시 검수 대상으로 보낸다. 변형이 불확실하면 자동 병합하거나 빈 값만으로 동일 상품으로 확정하지 않는다. 신규 양조장·브랜드도 검수된 식별값을 잠가 중복 생성을 줄이고, 유사 이름은 수동 확인한다.

그 트랜잭션에서 양조장·브랜드 연결 또는 생성, SAKE insert, 출처·대표 이미지 연결, 추천 프로필 insert, 1회 승인 매핑, 상태 변경과 감사 이벤트를 함께 커밋한다. 잠금 순서는 제보 → 식별 등록표 → 양조장·브랜드·상품으로 통일한다. UNIQUE 충돌이면 기존 결과를 반환할 수 있는 동일 작업인지 확인하고 다른 제보 충돌이면 검수로 돌린다. SQL insert가 실패하면 공개 행과 승인 상태가 함께 롤백된다.

## API·화면·권한

API는 기존 JSON·Bearer 규칙을 따른다. 제안 경로는 다음과 같다.

| 권한 | 경로 및 동작 |
| --- | --- |
| 회원 | `GET /api/user/catalog/breweries`, `GET /api/user/catalog/brands?breweryNo=…` 기존 항목 검색. 이름 검색·페이지 크기 상한·커서 적용 |
| 회원 | `POST /api/user/sake-submissions/uploads` 제한된 multipart 업로드. 이후 `POST /api/user/sake-submissions`로 payload와 소유 첨부 ID 제출. 업로드부터 제출까지 만료 시간 적용 |
| 소유 회원 | `GET /api/user/sake-submissions`, `GET /api/user/sake-submissions/{id}`, `POST …/{id}/revisions`, `POST …/{id}/cancel`. 자신의 요청과 공개 가능한 결정 사유만 반환 |
| 관리자 | `GET /api/admin/sake-submissions` 상태별 목록, `GET …/{id}` 상세·차이·감사, `GET …/{id}/duplicates` 중복 후보, `POST …/{id}/revisions` 수정, `POST …/{id}/decisions` 승인·반려·보완 요청. 이미지 승인 준비를 큐에 넣는 경우 `202`와 작업 상태를 반환 |
| 소유자·관리자 | 각 `/api/user/**`·`/api/admin/**`의 제보 하위 `attachments/{assetId}`에서 접근 검사 후 스트리밍. `Cache-Control: private, no-store`와 MIME·`nosniff` 적용 |
| 공개 | 기존 목록·상세 응답의 `imageUrl`은 활성 승인된 자산의 게이트웨이 URL을 필요 시 반환한다. 객체 키와 비공개 제보 데이터는 응답에서 제외 |

클라이언트는 버전과 Idempotency-Key를 보낸다. 인증 없음 401, 역할 부족 403, 다른 회원의 제보·첨부는 404, 오래된 버전·중복 활성 작업 409, 바이트 초과 413, MIME 거부 415, 필드 오류 422, 빈도·할당량 초과 429를 제안한다. 오너 판정은 JWT subject를 쿼리 조건에 포함하고 본문 회원 번호를 신뢰하지 않는다. 관리자 역할은 기존 보호 경로와 서비스 수준 확인을 함께 사용한다. JWT 역할은 발급 당시 값이므로 승인·비공개 미리보기에서 현재 `MEMBER_AUTHORITY`를 재확인해 권한 철회를 반영한다. 최초 관리자는 별도 승인·감사 가능한 운영 절차로 기존 계정에 부여한다. 가입·회원 수정·제보 API에 권한 설정을 노출하지 않고 저장소에 관리자 비밀번호를 두지 않는다.

본문과 업로드 바이트를 앞단과 앱에서 제한한다. 회원별 제출·업로드 빈도, 미처리 수·보관 바이트 쿼터, IP 공유 환경을 고려한 보조 제한을 제안한다. 배포 전 실제 임계값을 결정한다. 같은 회원의 반복 첨부는 해시로 중복 저장을 줄이되 회원 간 존재 여부를 노출하지 않는다. 스크립트가 포함된 원문·설명은 HTML로 렌더링하지 않는다. 서버에서 필드 길이, 문자, 수치 범위, URL 스킴을 검증하고 파라미터 바인딩을 사용한다. 출처 링크는 텍스트 또는 안전한 링크로 표시하며 서버가 가져오거나 썸네일을 자동 생성하지 않는다.

회원 화면은 기존 양조장·브랜드 검색, 신규 정보 입력, 선택적 이미지·권리 설명, 오류·용량 안내, 내 제보 목록과 보완·취소 흐름으로 구성한다. 관리자 화면은 큐, 원본과 수정본 비교, 인증된 미리보기, 중복·연결 후보, 권리 확인, 사유 입력, 처리 상태 및 충돌 새로고침을 제공한다. 프런트 권한 표시는 보조 UI로 활용한다.

## 이미지 공개와 장애 복구

개발 버킷, 제보 비공개 버킷, 공개 전달 전용 버킷을 분리한다. 전달 전용 R2 원본도 직접 공개하지 않고 게이트웨이가 DB의 `ACTIVE` 객체만 익명 제공하는 방식으로 시작한다. 제보 API는 비공개 쓰기, 검수 전달은 비공개 읽기, 승격 작업은 비공개 읽기·전달 영역 조건부 쓰기·검증, 공개 게이트웨이는 전달 영역 읽기만 가진다. 삭제·정리는 별도로 승인된 자격증명을 사용한다. 서버의 키·Secret은 브라우저에 전달하지 않는다. 사용자 업로드 바이트를 검증하며 사용자가 제출한 임의 URL은 출처 증거로만 보관한다.

IMG-03A의 JPEG·PNG 시그니처·디코딩, 바이트·해상도·픽셀 제한, 메타데이터 제거, 원본·변환 SHA-256과 버전형 키를 재사용한다. 제보 저장에는 내부 자산 식별자와 변환 버전·콘텐츠 해시를 사용하고 공개 승격에는 승인된 자산 버전에서 결정적인 키를 만든다. 기존 Tools의 상품 번호 기반 키는 호환을 유지하고 새 키 형식의 검증 스키마는 IMG-03B에서 설계한다. 증거·사용 범위·기간·철회를 서버가 확인한다. 업로드 동의는 권리 확인 자료 중 하나로 취급한다.

1. 비공개 객체는 조건부 PUT과 GET으로 해시·MIME·길이를 검증한 뒤 참조를 활성화한다. 업로드가 실패하면 제보 또는 첨부의 실패 상태를 기록한다.
2. 관리자의 승인 요청을 DB 작업으로 커밋한다. Worker는 짧은 임대와 시도 번호로 작업을 획득해 트랜잭션 밖에서 권리를 재검증하고 전달 전용 버킷에 조건부 PUT·GET을 수행한다. 키가 있으면 바이트를 재검증한다. 그 동안 게이트웨이는 전달하지 않는다.
3. 최종 DB 트랜잭션이 검색·추천 공개와 활성 이미지 참조를 전환한다. R2 PUT 이후 DB 실패 또는 응답 유실이 발생해도 동일 job·키로 재시도한다. 저장 해시가 충돌하면 덮어쓰지 않고 검수로 보낸다.
4. 미연결 객체는 작업·생성 시각으로 추적한다. TTL 이후 미완료 작업과 활성 참조를 다시 확인한 뒤 승인된 정리 절차로 삭제한다. 승격 장애와 DB 오류는 다른 이유로 기록한다. 오래된 worker는 임대 세대·행 버전 검사로 공개 전환을 거부한다.
5. 권리 철회·삭제 요청에서는 우선 DB에서 비활성 전환해 게이트웨이가 제공을 중단하게 한다. 초기 캐시 정책은 `no-store`를 제안한다. CDN 사용 시 경로·태그 purge 및 전파 확인이 필요하며, 실패는 재시도 가능한 작업으로 남긴다. 표기·정정 이력과 이전 자산의 권리 보존 범위를 감사에 기록하고, 삭제·비공개 요청에 따라 DB 정정 및 객체 격리를 수행한다. 이미 전달된 사본까지 회수된다고 가정하지 않는다.

## 검색·추천 반영과 모듈 공유

승인 시 프로필 범위를 같은 트랜잭션에서 계산하고 값이 없으면 NULL을 유지한다. 승인 이전 행은 공개 조회에 존재하지 않으므로 검색 및 AI 후보에 포함되지 않는다. 승인 행은 공개 검색과 신규 생성 후보에 반영한다. 점수·상위 40 제한 때문에 모든 추천에 노출을 보장할 수는 없다. 음식명 기반 공용 캐시(`RECOMMEND_SAKE`)는 이전 후보와 이유를 재사용하므로 승인만으로 자동 갱신되지 않는다. 초기 제안은 기존 캐시 계약을 유지하면서 활성 상품·자산만 렌더링하고, 새 후보 반영을 위한 공용 캐시 만료 또는 카탈로그 버전 도입은 별도 정책 검토다. 제외로 결과가 3건 미만이면 기존 예외 조건에 맞춰 정상 재생성 경로를 검증한다. 사케→음식 캐시는 내부 상품 번호로 접근하며 새 상품의 첫 요청에 생성된다. 유료 개인 스냅샷·멱등성·차감 조건은 유지하고, 철회된 이미지 URL의 전달 중단은 활성 게이트웨이에서 보장한다.

| 공유 대안 | 영향 |
| --- | --- |
| 공통 Java 모듈과 Gradle composite build | **제안.** `backend/image-core`를 독립 Java 라이브러리로 두고 Backend·Tools가 각 settings에서 `includeBuild`로 참조한다. Backend Docker 컨텍스트는 유지할 수 있지만 Dockerfile과 관련 ignore 규칙에 해당 하위 디렉터리 포함이 필요하다. Tools는 저장소의 Backend 하위 모듈을 포함해 빌드한다. 기존 양쪽 Wrapper와 CI 진입점을 유지한다. |
| 루트 Gradle 멀티프로젝트 | 공통 의존 관리에 유리하지만 독립 Wrapper, CI 작업 디렉터리, Docker 컨텍스트·복사 경로에 변경이 생긴다. |
| 사내 아티팩트 게시 | 체크아웃을 분리해서 빌드할 수 있지만 버전 배포, 레지스트리 권한, 접근 설정 및 공급망 관리 비용이 추가된다. |

공통 모듈에는 프레임워크 없는 바이트 검증·변환, 미디어 메타데이터, 해시, 저장 인터페이스와 R2 어댑터를 둔다. HTTP 다운로드와 출처 요청 정책은 Tools 경계에서 사용할 수 있게 유지한다. Backend의 JWT·권리 원장·공개 게이트웨이와 Tools 실행기는 각자의 책임으로 둔다. 기존 `ImageTransform`과 상태 enum의 결합은 공통 예외·사유 계약으로 분리할 수 있다. 실제 추출은 Docker Compose 외에 CI, Jenkins/OCI 빌드 진입점과 개발 Wrapper 경로를 먼저 대조하고 동일 계약으로 양쪽 빌드·테스트를 통과한 뒤 적용한다.
