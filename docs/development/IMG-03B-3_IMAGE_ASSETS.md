# IMG-03B-3 이미지 자산과 공개 제공

기준 main은 `a169feb8ae925d96f8e58e534724bf6206279b61`이다. 사용자 제공 Antigravity PASS와 PR #14 병합·원격 CI 기록은 공통 모듈 문서에 각각 남겼다. [IMG-03B-2 검증](IMG-03B-2_IMAGE_CORE.md#최종-독립-qa-및-병합)

## Flyway V10과 권리 기록

- `IMAGE_ASSET`에는 사케 번호와 독립적인 서버 발급 UUID, 출처 유형, 증거 참조, 원본과 변환본의 MIME·길이·해상도·해시와 변환 버전을 기록한다. 제한과 포맷을 통과한 결과만 `TRANSFORMED` 행으로 저장한다. 부적합 입력이나 변환 실패는 호출자에 반환한다. UGC-01에서 제출 리비전과 실패 정보를 보존할 수 있다.
- `IMAGE_OBJECT`는 자산마다 영역별 한 행을 갖는다. 영역·키의 UNIQUE와 실제 자산 FK를 갖는다. 성공한 저장의 검증 시각·길이·SHA-256을 기록한다. 새 키는 `asset/{uuid}/{transformVersion}/{sha256}.{jpg|png}` 형식이다. 이미지 원본 파일명은 키에 사용하지 않는다. Tools의 기존 `sake/{no}/...` 경로는 유지한다.
- `IMAGE_RIGHTS_EVENT`는 유효 기간, 증거, 판단 주체와 시각을 별도 행에 보존한다. 미검수는 이벤트 없음으로 표현한다. 최신 이벤트의 유효한 `GRANTED`와 `PUBLIC_WEB` 범위가 필요하다. 이 범위에는 전달용 복제와 웹 제공이 포함된다. 더 좁은 지역·기한·표기 조건은 근거와 전달 정책으로 집행할 수 있을 때만 승인해야 한다. V10은 기간 시작·종료를 제공 시점에 UTC로 검사한다. 변경이나 철회는 이전 연결을 닫고, 재승인 후에는 명시적 재연결이 필요하다.
- `SAKE_IMAGE`는 기존 `SAKE.no`와 동일 자산의 객체·권리 이벤트를 실제 FK로 연결한다. 상품 행 잠금과 생성 열의 UNIQUE로 활성 대표 이미지가 한 개를 넘지 않게 한다. 교체가 실패하면 기존 연결 닫기도 롤백한다. 철회된 행은 이력과 fallback 차단 근거로 유지한다.

V10은 기존 테이블을 백필하거나 변경하지 않고 신규 테이블과 뷰를 추가한다. MySQL에서 개별 DDL이 커밋된다. 적용 중 오류가 발생하면 생성된 객체, Flyway 이력 및 데이터 유무를 먼저 점검한다. 격리 재현과 승인된 복구 절차로 객체를 정리한 뒤 repair·migrate를 수행한다.

## 저장 구성과 장애 복구

Backend는 `IMAGE_STAGING_R2_`와 `IMAGE_DELIVERY_R2_` 접두사 아래 각각 `ENDPOINT`, `BUCKET`, `REGION`(기본 `auto`), `ACCESS_KEY_ID`, `SECRET_ACCESS_KEY`를 서버 환경에서 읽는다. 두 영역은 별도 버킷·키를 사용하며 두 버킷의 원본 공개 접근은 비활성으로 유지한다. 공개 전달은 Backend에 위임한다. Backend용 자격증명은 버킷을 각각 제한하고 GET·조건부 PUT에 필요한 권한만 부여한다. 브라우저에 자격증명 또는 버킷 URL을 전달하지 않는다. Tools의 개발 버킷 스모크에는 기존 변수와 명시적 실행 조건을 계속 사용한다. 저장소 설정 없이 기존 앱은 시작한다. 저장이 필요할 때는 안전하게 실패하고 공개 게이트웨이는 저장 경로를 사용할 수 없으면 503을 반환한다.

1. 신뢰된 호출자가 제출/작업에 저장한 UUID로 `stage`를 실행한다. 같은 UUID의 원본·변환본 또는 증거가 달라지면 충돌이다. DB에 출처와 불변 이미지 정보, 영역별 객체 의도와 시도 번호를 짧은 트랜잭션으로 기록한다.
2. 트랜잭션 외부에서 기존 객체 GET 또는 조건부 PUT 후 실제 GET으로 MIME·길이·SHA-256·캐시 메타데이터를 검사한다. 승인된 전달용 복제는 DB에 권리가 유효할 때 시작하며 STAGING의 검증된 변환본을 읽어 재인코딩 없이 복제한다. 최대 한 개의 이미지 처리 및 네 개의 공개 GET을 JVM마다 허용한다. 후속 HTTP 업로드는 이 한도 외에도 입력 바이트와 회원별 요청·저장량을 제한해야 한다.
3. 현재 시도만 짧은 후속 트랜잭션에서 `VERIFIED` 또는 실패로 전이할 수 있다. 일시적 I/O와 PUT 후 객체가 아직 보이지 않는 경우는 `RETRYABLE_FAILURE`다. 일치하지 않는 바이트·메타데이터·유효하지 않은 변환본은 `PERMANENT_FAILURE`로 조사한다. PUT·GET 뒤 DB 반영 실패 또는 응답 유실은 `PENDING`을 남길 수 있다. 같은 UUID·키로 다시 실행하면 기존 바이트를 검사하고 검증 결과를 기록한다.
4. 별도 공개 트랜잭션에서 최신 권리와 검증된 DELIVERY를 다시 확인한다. 재처리나 철회 중에 남은 객체는 공개 조건을 만족하기 전까지 전달되지 않는다. 작업자는 지속성 작업 큐의 임대·시도와 이 객체 시도를 연결해야 한다. 소유권 및 활성 상태를 확인하지 않은 삭제, 자동 삭제, 강제 덮어쓰기는 구현하지 않았다. 고아는 키·시도·증거를 대조해 별도 승인 경로로 처리한다.

## 조회와 호환성

익명 공개 경로는 `GET /api/images/sakes/{sakeNo}/{assetId}`다. 버킷·객체 키 입력은 받지 않는다. `PUBLIC_SAKE_IMAGE`는 활성 대표 연결, 해당 자산의 DELIVERY 검증·저장 메타데이터, 유효한 최신 권리, 철회 이력을 함께 본다. 바이트를 제한된 버퍼 하나에 받아 해시를 확인한 뒤 동일 연결의 현재 공개 여부를 재확인한다. 성공 응답에는 등록된 MIME, 실제 길이, `nosniff`, `no-store`를 적용한다. 철회가 두 번째 검사 이후에 발생하면 이미 전달 중인 응답까지 회수할 수 없다. 버킷 직접 공개나 CDN은 현재 계약에 포함하지 않는다.

같은 공개 판단을 적용하는 `CATALOG_SAKE_IMAGE_URL`로 목록·검색·상세와 공용 추천 조회에서 관리 경로를 우선한다. 관리 대표 연결 이력이 없는 상품은 기존 `SAKE.image_url`을 사용한다. 이미 관리 대표 연결을 만든 상품은 철회·만료·검증 손실 시 NULL이다. 유료 추천의 저장된 JSON은 보존하고, 응답할 때 관리 상품의 `imageUrl`만 이 정책으로 다시 계산한다. 멱등 재열람과 기록 상세에도 같은 조건을 적용하며 추천 이유와 크레딧 거래는 그대로 사용한다.

## 공통 모듈 P3와 후속 단계

`ImageTransform.Output`의 생성자를 비공개화하고 입력과 반환 바이트를 분리했다. 검증 저장 경계에서 키·MIME·길이·SHA-256과 실제 포맷·해상도를 다시 확인한다. 두 Wrapper에서 공통 XML 검사를 실행한다. APNG·PNG CRC·초과 입력·위조·변환 뒤 바이트 변경을 공통 테스트에서 검사한다. R2 어댑터가 URLConnection을 명시적으로 구성하므로 S3가 기본으로 끌어오는 Apache/Netty 클라이언트를 해당 의존성에서 제외했다. Google GenAI의 기존 클라이언트는 변경하지 않았다.

UGC-01은 제출·리비전·소유권, 용량·빈도 제한 및 비공개 미리보기를 구현한다. UUID, 작업 상태 및 권리 증거는 서버에서 발급·검증한다. UGC-02는 관리자 권한 검증과 승인 시점의 영속 작업·재시도·권리 재검사 및 최종 공개 트랜잭션을 담당한다. IMG-03C도 같은 자산·검증 계약을 사용한다. 기존 추천 SQL 수정, 구버전 Tools 쓰기 차단, UGC 승인 시 V9 잠금 준수는 운영 활성화 선행 조건이다.
