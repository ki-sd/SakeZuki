기준 main은 63a8d1de1bd82403953efb5fb88eada58f5cf303이다. PR #16의 사용자 제공 QA와 원격 증거를 구분해 기록했다. [UGC-01 최종 독립 QA](UGC-01_QA_PR16.md#최종-독립-qa와-병합)

## 경로와 권한

모든 경로는 /api/admin/sake-submissions 아래에 있다. Spring Security JWT ROLE_ADMIN에 더해 현재 MEMBER와 MEMBER_AUTHORITY를 DB에서 확인한다. ADMIN 역할을 JWT 발급 이후 잃은 회원은 403, 비활성 회원과 익명은 401이다. 식별자는 서명된 subject만 사용한다. 읽기 응답에 회원 번호, 이력 작성자 번호와 역할이 포함되며 주소·이메일·연락처·인증 정보는 선택하지 않는다.

| 요청 | 계약 |
| --- | --- |
| GET 기본 경로 | 상태, 정렬 CREATED/UPDATED(기본), q, page, size 지원. 0부터 페이지 번호, 기본 20·상한 50건. 이름과 현재 요약만 투영. JSON null과 누락된 이름은 검색에서 제외하며 실제 문자열은 기존 바이너리 비교를 사용. 정렬은 시각, ID 내림차순 |
| GET /{id} | 현재 상태·버전, 최초·현재·중간 리비전, 원자료와 작성자, 첨부·검증·권리 상태, 감사 이벤트 |
| GET /{id}/attachments/{assetId} | 검수 중인 제보의 불변 리비전에 연결된 검증된 STAGING 이미지 |
| GET /{id}/duplicates | 현재 리비전 기준 후보와 매칭 근거, 추가 검토 차이, 외부 출처 식별자와 전체 절단 여부 sourcesTruncated |
| POST /{id}/revisions | expectedVersion, reason, data. PENDING만 ADMIN_REVISION으로 수정 |
| POST /{id}/decisions | UUID Idempotency-Key, expectedVersion, revisionNo, decision, reason. REQUEST_REVISION과 REJECT 지원 |

입력에는 UGC-01과 동일한 16KiB JSON와 중복 키·미등록 속성·후행 토큰·스칼라 타입 제한을 적용한다. 사유는 한 줄 최대 500자다. 수정의 data는 검증된 전체 DTO이며 설명은 기존 LF 정규화를 사용한다. 미지원 결정 및 잘못된 입력은 422, 없는 대상은 404, 상태·버전·키 충돌은 409다.

## 검수 트랜잭션과 첨부

쓰기의 잠금 순서는 MEMBER(행위 관리자, FOR UPDATE) → MEMBER_AUTHORITY(ROLE_ADMIN, FOR SHARE) → CATALOG_SUBMISSION(FOR UPDATE)다. 소유 회원 행의 별도 잠금을 요구하지 않는다. 계정 UPDATE와 권한 DELETE/UPDATE는 이 행에서 직렬화된다. 권한 철회를 먼저 커밋하면 쓰기를 거부한다. 검수가 먼저 행 잠금을 잡으면 권한 철회는 그 검수 커밋 뒤 반영된다. 운영 권한 변경 절차가 두 테이블을 모두 잠글 때도 회원→권한 순서를 사용한다. UGC-01의 소유자 잠금, V9 공개 카탈로그 잠금 및 크레딧 원장은 각 기존 경로에서 유지한다.

관리자 수정은 PENDING에만 적용하고 NEEDS_REVISION의 사용자 보완은 기존 경로에서 처리한다. 원본을 보존하고 현재 리비전을 부모로 추가한다. 새 리비전, 버전, 감사 이벤트가 함께 커밋된다. 이전 첨부를 유지할 때 사용자 동의와 설명이 동일해야 한다. 제외할 때 첨부와 권리 설명·동의 필드를 함께 비운다. 새 첨부로 교체하거나 직전 리비전에서 제외한 첨부를 관리자가 다시 붙일 수 없다. 기존 이력에서 첨부와 사용자 동의는 보존된다.

V12는 결정 영수증의 영속 멱등성을 위한 SUBMISSION_REVIEW_DECISION만 추가한다. 회원별 UUID 키는 대상 제보 ID와 요청의 해시에 묶이며, 같은 입력은 원래 결과를 반환한다. 철회한 관리자나 다른 입력은 재생할 수 없다. PENDING→NEEDS_REVISION 또는 REJECTED의 변경, 버전·대상 리비전 검증, 감사 이벤트, 영수증이 한 트랜잭션에서 커밋된다. 보완이 제출되면 새 리비전이 PENDING이 되고 예전 결정은 그 리비전으로 승계되지 않는다.

## 비공개 미리보기와 후보

PENDING·NEEDS_REVISION, 활성 소유 회원, 제보의 불변 리비전 연결, READY 첨부, VERIFIED STAGING, 현재 권리에서 DENIED·REVOKED가 아닌 상태를 요구한다. 종료 상태와 고립된 첨부는 미리보기를 제공하지 않는다. 사용자·관리자 비공개 미리보기는 JVM당 2개 슬롯을 공유하며 공개 게이트웨이의 기존 4개 슬롯은 별개다. 버킷 대신 서버 경로를 반환한다. 저장소에서 바이트를 읽은 후 현재 관리자 역할, 첨부 관계, 객체와 검증 세대를 다시 확인한다. 네트워크 I/O 동안 트랜잭션을 보유하지 않는다. 응답에는 검증된 MIME·길이, private, no-store 및 nosniff를 적용한다.

중복 검색은 공개 이름·가나의 동일값과 길이 2자 이상 접두사를 MySQL 기존 collation으로 비교한다. 저장 이름은 정규화하여 변경하지 않는다. 일치 이름 수, 양조장·브랜드·특정명칭의 일치, 내부 번호로 순위를 정한다. 기존 관계는 내부 번호, 신규 제안은 일본어·한국어 이름의 열 collation 판정으로 비교한다. 같은 판정이 순위와 검수 차이에 쓰인다. 결과는 최대 20건, 외부 출처 키는 선택한 후보의 배치 최대 200건이다. 추가 출처가 있으면 sourcesTruncated가 true다. 카탈로그에 구조화된 용량·변형이 없으므로 확인 필요 필드로 표시하고 제출값을 함께 반환한다. 후보는 검수 자료다.

## UGC-02B/C 인수인계

- **02B**는 검토 리비전 번호와 기대 버전, 승인 결과의 제보 1:1 매핑, 확인된 상품 식별자와 관계 고유 제약을 둔다. V9 GUIDE_CATALOG_WRITE_MUTEX, 구버전 Tools 쓰기 차단, 추천 SQL의 양조장 조인·빈 조건 문제를 확인한 뒤 양조장·브랜드·사케·출처·추천 프로필을 같은 공개 트랜잭션에서 기록한다. 기존 캐시는 현재 계약을 유지하며 신규 후보 갱신 정책은 별도 검토한다.
- **02C**는 사용자 동의와 관리자 권리 판단을 분리한다. 승인 작업 중 보완·취소를 차단하고 영속 작업 임대·작업 세대·V10 객체 세대를 연결한다. STAGING→DELIVERY 조건부 저장과 GET 검증 후 별도 트랜잭션에서 관리자 권한·리비전·권리·객체를 재확인한다. 응답 유실·DB 실패 뒤 복구, 참조 없는 객체 관리, UGC-01 임대 교차 경합과 공용 ImageAssetService 자원 경쟁을 함께 검토한다.

## 검증 및 독립 QA 범위

로컬 검증 코드 3db41eeaa4d8c9f42b75a2c8759872ca3e0eb313. 검증용 MySQL 8.4.13, Fake Storage 및 모의 S3를 사용했다. V1–V11은 기준 main과 동일하다.

- 깨끗한 V1–V12 초기화와 V11→V12 업그레이드에서 시드 10,337건 및 전환 출처의 보존을 확인했다.
- 실제 MySQL 경쟁에서 관리자 리비전·반려·보완 요청과 사용자 취소, 두 관리자 결정, 관리자 리비전과 결정, 사용자 보완을 확인했다. 역할 DELETE가 커밋되기 전 동시 결정의 FOR SHARE 대기를 MySQL processlist에서 관찰했고, 선행 철회 커밋 뒤 403과 기존 감사 이력을 확인했다. 결정 영수증 삽입 실패의 상태·이력 롤백을 검증했다.
- 중복 조회에 사용한 실제 SQL을 별도 순수 시드 스키마에서 EXPLAIN ANALYZE했다. 테이블 스캔 10,337행 1회, 이름 조건 일치 194행, 반환 20행이었다. 양조장·브랜드 PK 조인은 각 20회, 전체 카탈로그 구체화는 없었다. 대표 실행의 루트 종료는 11.4ms다. 외부 키는 별도 배치 SQL로 읽는다. 운영 부하 측정은 미실행이다.
- 모의 STAGING 바이트와 메타데이터 손상, 저장소 오류, 미리보기 중 관리자 권한·계정·권리 변경, 공유 슬롯의 경합 및 반환을 검증했다.
- Tools Wrapper의 :image-core:cleanTest cleanTest test, Backend Wrapper bootJar, scripts/test_auth_integration.py --e2e를 사용했다. JVM 200개 중 image-core 11, Tools 기본 69·MySQL 17, Backend 기본 28·MySQL 75였다. 실패·오류·스킵은 0개였다. 선행 카탈로그 45건 경쟁과 실제 MySQL 1205 재시도를 재검증했다. 최종 Chromium 및 원격 결과는 PR 검사를 참조한다.

Antigravity 집중 범위는 발급 후 역할 철회와 두 잠금 순서, 동시 결정·취소·보완, 같은 요청 키와 감사 이벤트 롤백, 기존 이미지 동의의 불변성, 권한·검증 세대가 바뀌는 미리보기, 후보 상한이다. 기존 HEAD의 독립 QA 결과와 수정 HEAD의 검증 상태는 [PR #17 QA 후속 기록](UGC-02A_QA_PR17.md)을 참고한다.
